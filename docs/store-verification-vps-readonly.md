# JUGEST 店舗「検証」v2 — VPS保存済み結果専用画面

## 目的と非目標
iPhoneで `v4PredictStore` / `modelPerformanceForShop` を同期実行すると、日数・台数増加に伴いブラウザを長時間ブロックする。店舗→検証のUIではこれらを実行せず、VPSが事前に計算・保存した結果だけを読み取る。判別数学・予測モデル・評価式・DB schemaは変更しない。

検証ページ内の二つのタブは **LIVE成績** と **過去検証**。既存の `store-model` / `store-replay` ナビゲーションアクションは維持するが、旧ボタン `data-model-run` / `data-replay-run` は置かない。UIは読み取り専用。

## VPS側の既存パイプライン
```
営業日データ取得・正規化
  → DAILY_ANALYSIS
     → SHADOW_PREDICT: 翌日を予測して不変スナップショットを保存
     → PRE model/store-read: もう一方の予測スナップショット
     → scoreAvailableComparisonDays: 実績取得後に固定予測を採点
     → HISTORICAL_COMPARE: targetDateより前だけを使ったwalk-forward比較
  → /api/vps/stores/:storeId/research/comparison?limit=90 [GET]
     live + historical を1回で返す
  → 店舗「検証」には集計と日別の成績だけを表示
```

これらのジョブの**実際の実行状態**は運用側の状態として別途確認する。APIの応答が空でもUI側で計算・自動ジョブ起動を行わない。ライブ予測と過去のwalk-forwardを混合しない。

## フロントエンド構造
- `vps-ui-store-verify.mjs`: 読み取りクライアント、店舗名ごとの60秒キャッシュ、読み込みの重複排除、HTMLのエスケープ、安全な指標表示
- `vps-ui-store-v2.mjs`: 既存の5タブナビゲーションはそのまま。検証タブでは旧画面を差し替え、VPS結果だけを表示。非同期応答後、店舗・画面・実際のDOMを照合して古い応答が混ざることを防止
- `vps-ui-store-v2.css`: 320pxでも読みやすいKPI・比較表・日別一覧
- `vps-browser-analytics.mjs` とサーバーの認証・比較APIは既存のまま使用。トークンはフロントの既存クライアントに委ね、新UI内で保存しない。

## 表示の契約
- LIVE: 日次固定予測の「採点日数、未採点日数、PRE版/現行版勝敗、Top1/3/5 lift、順位相関、Coverage、日別の採点結果」
- 過去: walk-forwardの「対象候補日・処理日数・採点日数、両予測の比較、日別結果」
- 未採点・準備中・取得エラー・認証不足・権限なしを区別する。実績がない期間を0点として扱わない。
- 日別は最大30件の詳細一覧、レスポンスはVPS側の90日上限。表示中の再計算はない。
- 手動「再取得」はGETのみ（予測の再学習や採点ではない）。
- 旧端末内の「モデル信頼度・設定P4+」とVPS評価の「lift/順位相関」は**違う指標**であり、数値を混在させない。

## 権限と店舗
既存VPS Collector Receiverの所有者として認証する。認証がない場合は「Collector連携が必要」、対象VPS店舗がない場合は「データなし」、403は「閲覧権限なし」とする。PIA公開閲覧Cookieの許可範囲を勝手に拡大せず、非公開モデル評価を公開しない。

## 店舗「傾向」の0/0対策
VPSにはデータがあるが従来の台番期待設定傾向がローカルにない場合、「0日/0台」を実データ不在と偽装しない。VPSの蓄積日数と最新台数を表示し、端末内の台番傾向が未同期であることを明記。空の判別計算ボタンを無効化し、VPSの保存済み投入パターンへ誘導する。
これは**台番別VPS期待設定ランキングの移植ではない**。それは別途解析基盤側で計画する。

## 検証
- レンダリング・権限不足・キャッシュ・非同期多重リクエストの単体テスト
- 320/375/390pxの実ブラウザ検証
- 複数店舗A/BのAPI応答の分離
- LIVE→過去→別店舗→再取得がGETだけで完結すること
- 数値の欠損、HTMLエスケープ、旧ボタンの不在
- 既存のフロント・VPS全体テスト、デプロイ前に確認

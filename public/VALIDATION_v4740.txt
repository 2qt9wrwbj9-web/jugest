JUGGLER / HANA HANA TOOL v4.7.4 VALIDATION — LAZY EXECUTION / PERFORMANCE

Scope
-----
Performance-only refactor on top of v4.7.3. Goal: preserve all analysis/judgement functionality while removing unnecessary work from startup and category navigation.

Structural performance audit
----------------------------
Baseline v4.7.3:
- initExternalStorage() called rejudgeAllExternalDays() after loading IndexedDB, forcing a full external-row judgement pass during startup.
- restored startup also had a rejudgeAllExternalDays() call path.
- queueAutoSave() used a 40ms debounce, so ordinary clicks could trigger near-immediate full state JSON serialization.
- Today Plan could compute all stores on category render.
- Trend/model/twin views could perform expensive calculation on category/filter entry.
- large result/history/matrix views could create substantially more DOM than visible on a phone.

v4.7.4:
- no rejudgeAllExternalDays() call remains in startup or initExternalStorage().
- compact IndexedDB unpack yields after roughly 1200 table rows.
- missing external derived values are generated lazily by ensureExternalJudged()/ensureExternalJudgedSync() only for requested data.
- autosave uses requestIdleCallback(timeout 1200ms) when available, otherwise a 450ms debounce; pagehide/beforeunload remain immediate.
- selected-store Today Plan is explicit; all-store comparison remains available only as an explicit heavy option.
- Trend filtering is staged and explicit; matrix DOM initially limits both table rows and date columns.
- Model Performance and Digital Twin/lifecycle are not computed merely by category entry.
- External history and single-evidence lists are incremental.

Limitations / next field check
------------------------------
- This validates semantic preservation and removes known eager work structurally; it is not an iPhone Safari benchmark.
- Full 180-day prediction, explicit all-store Today Plan, and optional 2/3-condition exhaustive exploration remain computationally heavy by design when requested.
- First priority after deployment: compare cold-start responsiveness, first category switch, repeat category switch, and first/repeat Today Plan on the real iPhone with the Kabukicho long-history database.
- If explicit heavy operations still cause unacceptable UI stalls after this lazy pass, the next architectural step is moving the longest CPU-bound analysis loops into a Web Worker. That is intentionally not part of this no-semantic-change lazy pass because it changes execution architecture and should be field-justified first.
